# Составление тест-кейсов — методология

Durable-руководство по проектированию тест-кейсов: как раскладывать проверки по уровням
тестирования, какие типы кейсов закладывать и каких принципов держаться при составлении.
Это про **дизайн набора**, не про прогон (прогон — `subagent-orchestration.md`,
раскладка по tier'ам — `tier-cluster-model.md`).

## Уровни тестирования (по цели)

Уровень кейса определяется **целью прогона**, а не слоем пирамиды (unit/integration/e2e —
ортогональная ось, см. `tier-cluster-model.md`). Набор уровней — не догма; для функциональной
проверки фичи/модуля релевантны:

| Уровень | Зачем | Когда / глубина |
|---|---|---|
| **Смоук** | «Вообще живо?» — фича стартует, golden path не падает | После каждого деплоя; 1–3 кейса, быстро |
| **Санити / проверка исправлений** | Узкая перепроверка конкретной области или **зафиксированного дефекта** | После фикса; точечно |
| **Приёмка** | Фича делает то, что просили — критерии тикета/спеки | На сдаче изменения; позитив по требованиям |
| **Регресс** | Изменение не сломало то, что работало раньше | Вокруг затронутой области; представительный реран |
| **Полное функциональное** | Исчерпывающая уверенность по модулю целиком | Периодически; негатив, границы, комплемент, TZ, матрицы |
| **Исследовательское** *(опц.)* | Неструктурированный поиск того, что скриптовые кейсы упускают | Ad-hoc |

## Типы кейсов и их раскладка по уровням

| Тип кейса | Представление | Смоук | Приёмка | Регресс | Полное |
|---|---|:--:|:--:|:--:|:--:|
| Golden / happy path | сценарий | ✅ | ✅ | ✅ | ✅ |
| Позитив по требованиям (критерии тикета/спеки) | сценарий | | ✅ | | ✅ |
| Реран представительных существующих сценариев | сценарий | | | ✅ | ✅ |
| Негатив / робастность | сценарий на правило | | частично | | ✅ |
| Граничные значения | сценарий | | | | ✅ |
| Комплементарное покрытие («тест на отсутствие») | сценарий | | частично | | ✅ |
| Темпоральное / часовые пояса | сценарий | | | | ✅ |
| Права (роли × статусы × действия) | **матрица-эталон** | | | | ✅ |
| Атрибуты (поле × условия → видимость/обязательность) | **матрица-эталон** | | | | ✅ |

Пояснения к нетривиальным типам:

- **Негатив / робастность («защита от дурака»).** Для любой фичи проактивно закладывать: кривой
  ввод/конфиг **не должен ронять процесс**; действие, требующее обязательного поля/комментария,
  отклоняется при его отсутствии; действие в недопустимом статусе/роли — запрещено. Негатив часто
  ловит больше дефектов, чем позитив, и его нельзя проектировать «по остаточному принципу».
- **Комплементарное покрытие («тест на отсутствие»).** Если правило задаёт значение **по условию** —
  проверить и обратное: условие не выполнено → значение остаётся **пустым/дефолтным**. Типовой
  пробел: покрыли только случаи, где значение проставляется, и забыли случай, где его быть не
  должно (напр. срок/дедлайн не задаётся явно → поле должно остаться пустым).
- **Темпоральное / часовые пояса.** Если поведение зависит от дат/времени — закладывать измерение:
  разные часовые пояса, границы суток, рабочий календарь и выходные/праздники, переход на летнее
  время (DST). Лёгкий источник скрытых дефектов, который позитив на одном поясе не вскрывает.
- **Матрицы-эталоны.** Комбинаторные измерения (права = роли×статусы; атрибуты = поле×условия) не
  разворачивать в сотни построчных прогонов — фиксировать **таблицей ожидаемого** (оракул) и из неё
  выводить точечные проверки.

## Сквозные принципы составления

1. **Источник истины — спецификация + реальный код, не догадки.** Перед тем как сохранить кейс,
   свериться по коду, что поведение реально реализовано (ветка могла уже получить фиксы). Утверждения
   спеки сверять с артефактами (модель/процесс/форма), а не принимать на веру.

2. **Гибридная глубина — под измерение.** Поведенческие потоки → несколько **представительных**
   сценариев на правило (не перебор всех путей). Комбинаторика (права, атрибуты) → **матрица-эталон**,
   из неё точечные проверки. Один формат не натягивать на всё.

3. **Каждый кейс размечен уровнем/целью.** У кейса есть тег уровня (смоук/санити/приёмка/регресс/
   полное). Из тегов **собирается набор под конкретную цель прогона** — один кейс может входить в
   несколько наборов (golden path — и смоук, и приёмка, и регресс). Без разметки набор превращается
   в плоский список, из которого нельзя быстро собрать нужный срез.

4. **Дизайн отделён от прогона.** Спроектировать кейсы и зафиксировать открытые вопросы можно **без**
   live-прогона. Такие кейсы помечаются явно («добавлен, не прогонялся»), открытый вопрос
   записывается **как вопрос**, а не «тихо решается» догадкой.

5. **Прогон = весь согласованный набор, без cherry-pick.** Когда набор согласован и идёт прогон —
   выполняются **все** кейсы, а не выборочно «удобные». Кейс, который сейчас прогнать нельзя
   (функционал не готов, нет данных/стенда), — это **не молчаливый пропуск**, а явный статус с
   причиной. Итог должен сходиться: `всего = пройдено + провалено + отложено(с причиной)`. Опасность
   cherry-pick в том, что пропускают обычно самые рискованные кейсы (негатив, границы).

6. **Удалять мёртвые кейсы.** Поведение, которое никогда не было реализовано и за годы никому не
   понадобилось, — выкидывать, а не тащить из шаблона/спеки только потому, что оно где-то записано.

7. **Ревью и расхождения «спека↔код» — открыто.** Замечания ревьюеров вносятся в кейсы и видно, что
   отработаны. Несовпадение спеки и кода — это **находка**, а не повод тихо «подогнать» кейс под одну
   из сторон: фиксировать сноской/маркером (`[code:?]`, `[form:?]`) или открытым вопросом с
   формулировкой «что именно расходится» и «к кому вопрос». Тест-набор остаётся честным оракулом.

8. **Резюме простым языком.** Уметь сказать словами: что протестировали, в чём убедились, какую цель
   закрыли — **до** разбора пробелов и метрик покрытия.
