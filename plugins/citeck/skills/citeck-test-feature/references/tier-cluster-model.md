# Reference: Tier & Cluster Model

DURABLE-ядро: как раскладывать кейсы по tier'ам и кластерам конфигов, ID-конвенции и done-criteria.
Платформо-агностично. Конкретные кластеры конкретной фичи — в `examples/` и в сгенерированном плане.

## Tier-модель (способ выполнения)

| Tier | Описание | Метод | Параллелизация |
|---|---|---|---|
| **A** | API-only (большинство кейсов) — `[HTTP]+[RA]+[LOG]+[U]` | scripted curl + Records API + лог-чек | Свободная (внутри одного кластера) — несколько субагентов параллельно |
| **B** | UI E2E smoke — `[PW]` | Playwright | Последовательно (один браузер на сессию) |

**Принцип:** UI-логика проверяется через REST API того же эндпоинта, что использует фронт. В Tier B
остаются только happy-path E2E (контракт фронт↔бэк), visual rendering и UX-зависимый gating. Это
держит число медленных UI-кейсов маленьким (обычно единицы), а остальное гоняется параллельно через API.

Tier-разметка проставляется в шапке каждого кейса: `Tier:`, `Cluster:`, `Tools:`, `Subagent:`.

## Cluster-модель (минимизация рестартов)

Кластер = набор кейсов, выполняемых при **одной** конфигурации сервиса. Цель — сгруппировать кейсы
так, чтобы менять `application.yml` / перезапускать сервис как можно реже.

- Кластер 0 — pre-flight + unit-suite (без запущенного сервиса / до старта).
- Кластер 1 — **default config** (большинство кейсов).
- Кластеры 2..N — по одному config-toggle каждый (feature-флаг off, лимиты, альт-провайдер, TTL и т.п.).

Правила:
- Внутри кластера сервис стартует **один раз**; кейсы гоняются в любом порядке (после smoke draft).
- Между кластерами — единичный edit `application.yml` (или patch исходника, если флаг
  не вынесен в конфиг) + restart.
- **Параллелизм невозможен МЕЖДУ кластерами** (один локальный сервис), но **внутри** кластера
  Tier A кейсы параллелятся.
- ⚠ **После последнего кластера — обязательный возврат к defaults** (откат `application.yml` и любых
  patch'ей исходника). Проверить `git status` перед MR: тестовых правок быть не должно.

### Шаблон смены кластера

```bash
# 1. Применить config (edit application.yml или patch + rebuild)
#    citeck: ai: <feature>: enabled: false   # пример

# 2. Restart сервиса
pkill -f '<service-process-pattern>' && sleep 2 && \
  ./mvnw spring-boot:run 2>&1 | tee target/logs/<service>.log &
# или docker restart <container>  — зависит от того, как запущен сервис

# 3. Wait ready
lsof -iTCP:<port> -sTCP:LISTEN          # либо curl health-check

# 4. Verify config применён
grep -i "<config-key>" target/logs/<service>.log   # либо проверить health-эндпоинт
```

### Return-to-defaults (после последнего кластера)
```bash
git checkout -- src/main/resources/config/application.yml \
                $(grep -rl '<patched-class>' src/main/kotlin 2>/dev/null)
# rebuild + restart при необходимости финал-smoke
git status   # ⚠ ничего тестового не должно остаться
```

## ID-конвенции кейсов

Префиксы по разделам — единый язык для отчёта и субагентов:

| Префикс | Раздел | Пример нумерации |
|---|---|---|
| `T` | Pre-flight (проверка инструментов) | T1–T7 |
| `S` | Smoke (стенд + toggles) | S1–S11 |
| `R` | Регрессия (existing behavior) | R1–R19 |
| `F` | Feature acceptance — направление 1 (напр. файлы) | F1–F23 |
| `I` | Feature acceptance — направление 2 (напр. изображения) | I1–I34 |
| `C` | Cross-cutting (console/network/logs/audit) | C1–C6 |
| `<X>-PM` | Provider/variant matrix внутри раздела | F-PM1–F-PM7 |

Буквы F/I/… привязываются к **направлениям** конкретной фичи — не фиксированы. Главное: одна
буква = один связный раздел, номера сквозные, в отчёте те же ID.

### Свёртка дублей
Если defect-регрессия фактически проверяется acceptance-кейсом — не гонять отдельно, пометить
`(folded) → <ID>` в отчёте. Самостоятельными оставлять только то, что не покрыто (чистый
`[HTTP]`/`[RA]`-сценарий без UI-двойника).

## Done-criteria (гейт готовности)

Не отмечать прогон готовым, пока:
- T-кейсы пройдены (или нерабочие инструменты явно зафиксированы);
- unit-suite зелёный;
- все R-кейсы пройдены без замечаний;
- feature-кейсы (F/I/…) пройдены или явно `SKIP` с обоснованием;
- provider/variant matrices пройдены минимум на одном варианте каждой строки;
- C-кейсы (console/network/logs/audit) — без ошибок;
- после config-кластеров выполнен return-to-defaults (`git status` чист).

Только после этого ветка готова к MR.
