## v3.10.0 (2026-06-30)

### 🆕 `citeck-test-feature` — методология составления тест-кейсов

Новый durable-reference `references/test-case-design.md` и привязка к шагу 4 (скоупинг). Скилл теперь
направляет не только КАК прогонять, но и КАК проектировать набор кейсов:

- **Уровни тестирования по цели** — смоук / санити (проверка исправлений) / приёмка / регресс /
  полное функциональное / исследовательское; раскладка типов кейсов по уровням таблицей
- **Типы кейсов** — golden path, позитив по требованиям, реран существующих, негатив/робастность
  («защита от дурака»), граничные значения, **комплементарное покрытие** («тест на отсутствие»:
  нет условия → значение пусто/дефолт), **темпоральное / часовые пояса** (TZ, границы суток,
  календарь, DST), матрицы-эталоны прав и атрибутов
- **Принципы составления** — источник истины = спека + реальный код (не догадки); гибридная глубина
  (потоки → сценарии, комбинаторика → матрицы); каждый кейс размечен уровнем/целью (наборы
  собираются по тегам); дизайн отделён от прогона («добавлен, не прогонялся»); прогон = весь
  согласованный набор без cherry-pick; удалять мёртвые кейсы; расхождения «спека↔код» фиксировать
  открыто (сноска/вопрос), а не подгонять; резюме простым языком до разбора пробелов

## v3.9.0 (2026-06-22)

### 🆕 Скилл `citeck-test-feature` — приёмочное тестирование фич платформы

Новый скилл `/citeck:citeck-test-feature` — durable-руководство и скаффолдер для приёмочного тестирования любой фичи Citeck на выбранном стенде:

- **Гид + скаффолдинг**: служит методологией (КАК тестировать) и при вызове генерирует датированную папку тест-плана в целевом проекте (`docs/plans/<date>-<issue>-test-plan/`) — README, кейсы, отчёты, промпты субагентов, фикстуры
- **Параметризуемый стенд**: на старте узнаёт и подтверждает целевой стенд (base URL + MCP-профиль + auth), привязывает все curl/Playwright/Records-операции к выбранному `base_url` — не хардкодит `localhost`
- **Safety deny-by-default**: деструктивные операции запрещены по умолчанию и разрешаются только на стенде, явно классифицированном как non-prod (стенд-политика `.test-stands.yml`); неизвестный стенд → fail-closed; обязательный workspace/run-id scoping
- **Идемпотентный скаффолдинг**: эксклюзивный create корня плана, не затирает отредактированные файлы, отчёты под уникальным run-id
- **Durable-ядро**: Records API + Playwright + gateway HTTP harness, tier/cluster-модель (A=API-параллельно, B=UI-последовательно), оркестрация субагентов, шаблоны и генераторы фикстур; citeck-ai как профиль-пример
- использует Citeck MCP + Playwright MCP + scripted HTTP

## v3.8.0 (2026-06-10)

### 🎉 Бесшовное продление сессии

Сессия больше не «истекает» каждые полчаса посреди работы — авторизация продлевается автоматически:

- PKCE-флоу теперь запрашивает scope `offline_access` — refresh-токен не привязан к браузерной SSO-сессии и живёт по offline-политике Keycloak (по умолчанию 30 дней с момента последнего использования, продлевается при каждом обращении). Пока инструментами пользуются хотя бы раз в месяц, повторный вход не нужен
- если клиенту в Keycloak scope `offline_access` не разрешён, флоу автоматически повторяется с обычным `openid` — поведение остаётся как раньше
- новый MCP-инструмент `reauthenticate` — когда переавторизация всё же нужна, ассистент вызывает его сам: открывается браузер для входа, после логина исходная операция повторяется автоматически. Запускать `/citeck:citeck-auth` вручную больше не требуется (скилл остаётся для первичной настройки и управления профилями)

## v3.7.0 (2026-06-08)

### 🆕 Человекочитаемое превью создания задач и комментариев

Новые read-only инструменты `preview_issue` и `preview_comment` показывают, что именно будет создано/изменено, в удобном для терминала виде — до реального запроса на запись:

- ссылки (проект, спринт, компоненты, теги, релизы, эпик, исполнитель, автор) резолвятся в имена и отображаются ссылками на объекты; нерезолвящиеся помечаются `⚠️`
- описание и комментарий рендерятся из Lexical-HTML в читаемый текст (заголовки, вложенные списки, жирный/курсив/код, ссылки, картинки, HTML-сущности) вместо сырой разметки
- тип и приоритет показываются ярлыками
- `preview_issue` сам выбирает режим: создание (по `type`) или обновление (по `issue`)

Инструменты помечены как read-only — их можно добавить в allowlist и вызывать без подтверждения.

Параметр `preview` удалён из `create_issue`, `update_issue` и `add_comment` — теперь эти инструменты всегда выполняют операцию, а предпросмотр делается отдельным `preview_*`.

### 🐛 Исправления

- `create_issue` записывал тип задачи в атрибут `type?str`, который сервер игнорирует, — любая задача создавалась с базовым типом `emodel/type@ept-issue` («Tracker issue») независимо от выбранного `task`/`story`/`bug`/`epic`. Теперь тип пишется в `_type?str` коротким именем, и задача создаётся нужного типа.

## v3.6.0 (2026-05-28)

### 🆕 Расширение полей и операций над задачами

`create_issue` и `update_issue` получили параметры для связывания задач между собой и с релизами:

- `fix_in_version` — целевые релизы (Target releases, атрибут `fixInVersion`)
- `affected_versions` — затронутые релизы (Affected releases, атрибут `affectedVersions`)
- `epic` — привязка к эпику (epicLink), одиночная ассоциация на ept-issue
- `links_relates` / `links_blocker` / `links_duplicate` / `links_clone` / `links_problem` — связи между задачами (множественные ассоциации `issue-links:*`)

Релизы принимают список рефов (UUID или полный `emodel/ecos-release-type@...`); связи и эпик — ключи задач (`PROJECT-N`) или полные рефы. Голые id автоматически префиксуются. Релизные рефы получаются через `query_releases`.

### 🆕 add_comment

Новый MCP-инструмент для добавления комментария к задаче — создаёт запись `emodel/comment` с атрибутами `text` (HTML) и `record` (ссылка на ept-issue). Поддерживает `preview` и пер-вызовный `profile`, как остальные мутирующие тулы.

### 🐛 Исправления

- `update_issue` записывал статус в атрибут `_state` вместо `_status` — операция возвращала `ok`, но реальный статус задачи не менялся. Теперь статус пишется в `_status`.

## v3.5.0 (2026-05-19)

### 🎉 Маршрутизация инструментов по разным окружениям

`ept_profile` и `records_profile` — новые поля в `credentials.json`, которые позволяют направлять разные группы инструментов в разные окружения Citeck. Типичный сценарий: трекер задач на проде, records-запросы локально.

- `ept_profile` — task-tracker инструменты: `search_issues`, `create_issue`, `update_issue`, `list_projects`, `set_project_default`, `query_sprints/components/tags/releases`, `query_comments`, `download_attachment`
- `records_profile` — `records_query` и `records_mutate`
- Каждая настройка независима и при отсутствии откатывается на `active_profile`
- Новые MCP-инструменты `set_ept_profile` и `set_records_profile` (пустая строка очищает настройку)
- Каждый затронутый инструмент также принимает разовый параметр `profile` для конкретного вызова
- `/citeck:citeck-auth` после настройки нового профиля предлагает назначить его как ept/records

### 🆕 Новое

- `list_profiles` — список настроенных профилей с не-секретными метаданными (url, auth_method, флаги `is_active`/`is_docs`/`is_ept`/`is_records`)
- `set_active_profile` — переключение активного профиля без повторного вызова `/citeck:citeck-auth`
- В ответе `test_connection` теперь возвращается имя активного профиля

### 🐛 Исправления

- Сообщение об ошибке в `resolve_docs_profile` ложно ссылалось на `docs_profile`, когда вызывающий явно передавал `profile=` с совпадающим именем — теперь сообщение корректно отличает явный override от резолва через настройку

## v3.4.0 (2026-04-17)

### 🎉 Поиск по документации Citeck

**/citeck:citeck-ask-docs** — новый скилл для семантического поиска по citeck-docs с синтезом ответа на основе найденных фрагментов.

- RAG-поиск через `/gateway/rag/api/rag/search` по репозиторию citeck-docs
- Два новых MCP-инструмента: `search_docs` и `set_docs_profile`
- Отдельный параметр `docs_profile` в `credentials.json` — можно работать с локальным Citeck, а документацию искать на другом сервере, где проиндексирован citeck-docs
- В ответах появляются прямые ссылки на опубликованную документацию (readthedocs) вместо относительных путей к файлам — URL собирается из `base_doc_url`, `docs_root_path` и `url_extension` в метаданных RAG-ответа
- `/citeck:citeck-auth` предлагает пометить профиль как источник документации сразу после настройки

## v2.0.0 (2026-03-06)

Мажорный релиз — полная переработка плагина Citeck для Claude Code.

### Общие библиотеки (`lib/`)
- **config.py** — управление профилями и credentials в `~/.citeck/credentials.json` (chmod 600, валидация имён профилей от path traversal)
- **auth.py** — OIDC password grant + Basic Auth fallback + поддержка PKCE, кэширование токенов по профилям, auto-refresh, обнаружение endpoint через `eis.json` + OpenID well-known, извлечение username из JWT
- **pkce.py** — браузерный PKCE OAuth flow с локальным HTTP-сервером
- **records_api.py** — HTTP-клиент для Records API с вложенным форматом запросов (sourceId, language, consistency, workspaces, sortBy)

### Новые скиллы
- **citeck-auth** — интерактивная настройка подключения (PKCE/password/basic), тест соединения, переключение профилей
- **citeck-tracker** — управление задачами Project Tracker:
  - `query_issues.py`: поиск с `--assignee me`, `--project` (workspace), `--sort`, `--status`, `--type`
  - `create_issue.py` / `update_issue.py`: с dry-run и подтверждением
- **citeck-changes-to-task** — генерация описания задачи из git changes с возможностью создания в Citeck

### Улучшения
- Скрипты **citeck-records** теперь используют общие модули из `lib/` вместо встроенной авторизации
- Кликабельная ссылка после создания задачи

### Тесты
- 204 юнит-теста, все с моками (без обращений к реальным сервисам)
