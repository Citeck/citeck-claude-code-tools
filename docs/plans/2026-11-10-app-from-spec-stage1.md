# Этап 1: приложение по ТЗ силами стороннего агента (минимальный прототип)

Рабочий план исполнения раздела 9 записки `citeck-ai/docs/plans/20261106-app-generation-to-external-agents.md`.
Ветка `feature/app-from-spec-stage1` от `master` 4.1.1. Начат 2026-11-10.

## 1. Отход от записки (указание владельца 2026-11-10)

- **Развёртывание — штатная загрузка архива приложения, без доработки `ecos-apps`.** Архив загружается мутацией
  `eapps/ecosapp@` с `_workspace` и `_content` (base64), так приложение и его артефакты попадают в пространство
  (`EcosAppService.uploadZip`). Каталог `AppDirWatcher` не годится: он загружает приложение глобально. Конец именно этой
  загрузки и текст ошибки берутся из журнала контейнера `ecos-apps` (проверено на стенде 2026-11-10, раздел 2); без доступа к
  журналу — вывод по статусам Records с пометкой «конец выведен».
- ralphex не используется, работа идёт в сессии. Pi ставится позже — приёмка через Pi ждёт его.

## 2. Проверено на локальном стенде 2026-11-10

- `POST /gateway/eproc/api/bpmn/auto-layout/transform` с Basic работает под `admin` и под обычным `fet`.
- `VALIDATE_GENERAL_BPMN` через `eproc/bpmn-def@` работает под `fet`; ошибка схемы приходит в `messages[].msg.msg`
  при HTTP 200.
- Загрузка архива через Records в пространство: артефакты `eapps/artifact@<вид>$<ws>:<id>`, ссылки внутри архива —
  `emodel/type@CURRENT_WS:<id>`. Загрузка в несуществующее пространство молча принимается с префиксом `DELETED_` —
  инструмент обязан создать или проверить пространство до загрузки.
- Одна загрузка обрабатывается под одним идентификатором трассировки: `Start artifacts uploading from source
  AppSourceKey(... SourceKey(id=<ws>:<app>, ...` → `Create new artifact revision entity ...(<вид>$<id>). Source:
  SourceKey(id=<ws>:<app>` → `Deploy status changed for <вид>$<id> from DRAFT to DEPLOYED|DEPLOY_FAILED`; ошибка —
  `Artifact deploy failed: <вид>$<id>. Errors:` и JSON на следующей строке. Неудачный артефакт платформа повторяет сама
  (FAILED → DRAFT → FAILED), поэтому статус Records сразу после загрузки может быть старым. Неизменённое содержимое —
  `Application content doesn't change`.

## 3. Состав

- `lib/guards.py`: список разрешённых стендов (`CITECK_ALLOWED_SERVERS`), режим генерации (`CITECK_GENERATION_MODE`) —
  `records_mutate` отказывает на источниках артефактов. Проверка стенда — в `records_api.request`, единой точке.
- `lib/bpmn_tools.py` + инструменты `bpmn_validate`, `bpmn_layout` (работают с файлом, ответ раскладки пишется в тот же файл).
- `lib/app_deploy.py` + инструмент `deploy_app`: проверки области записи, архив из каталога, загрузка, ожидание конца
  загрузки по журналу, итог по каждому изменённому артефакту, коммит каталога приложения.
- Навык `citeck-app-from-spec`: порядок работы, цикл, журнал итераций, справочник (`references/`).
- Временное (записка, раздел 9.7): проверки области записи в `deploy_app`, раскладка и правило повтора в плагине, копия схем.

## 6. Найдено при приёмке и исправлено

- Существование записи нельзя проверять атрибутом `id`: у несуществующего `emodel/workspace@x` платформа возвращает его
  эхом. Проверка — `_notExists?bool`.
- Загрузка в пространство, которое `ecos-apps` недавно видел несуществующим, привязывается к `DELETED_<ws>` (кеш
  пространств, проходит меньше чем за минуту). `deploy_app` удаляет такую запись приложения и повторяет загрузку до 90 с.
- Отказ мутации Records API приходит как HTTP 500 с текстом в теле: `bpmn_validate`, `deploy_app` и `records_mutate`
  (новое поле `platform_errors`) разбирают тело ответа.
- Предел платформы: определение BPMN длиннее 100 000 символов не развёртывается (`JAXP00010003`), а
  `VALIDATE_GENERAL_BPMN` его пропускает — записано в `platform-traps.md`.

## 6а. Ревью Codex, круг 1 (2026-11-10): 14 находок, все исправлены

Отчёт: в журнале сессии. Высокие: (1) строки журнала без пространства принимались за результат своей загрузки —
теперь итог засчитывается, только когда журнал и Records этого пространства согласны, чужие приложения общего прохода
отбрасываются; (2) старый `DEPLOY_FAILED` переживал повтор — побеждает последнее состояние, `ok` требует подтверждённого
конца; (3) ошибки импорта до ревизии давали успех — разбираются `Artifacts can't be received` / `Artifact uploading
failed`, исход `import_failed`; (4) запасной путь по Records мог выдать ложный успех — без журнала исход `unconfirmed`,
`ok: false`; (5) `default` — глобальное пространство, отказ; (6) цели патчей — `app/artifact-patch` обязан указать своё
пространство, `app/patch` не может называть чужие пространства и глобальные артефакты. Средние: системный id
пространства для ключа источника и ссылок; ответ `DELETED_` больше не удаляется и не повторяется — загрузка
отслеживается под этим ключом (приложение всё равно в пространстве, проверено вживую); после таймаута раскладки повтора
нет; проверка прав — по тексту, блочный YAML не прячет ссылку; `records_mutate` отказывает на чужое пространство в id,
`_workspace`, `_parent`; добавлены источники `emodel/permission-settings*`; у `app/patch` пометка «только
зарегистрирован». Низкая: коммит на каждое развёртывание, также без изменений файлов.

При перепроверке на стенде найден ещё один дефект и исправлен: журнал читается с запасом в 2 с, туда попадала строка
«content doesn't change» предыдущего развёртывания — разбор начинается с последнего запроса загрузки этого приложения.

## 6б. Ревью Codex, круг 2: 12 из 14 закрыты, 2 не закрыты, 5 новых — все исправлены

- №1 (высокая): статус засчитывается, только если Records этого пространства показывает конечный статус, сохранённый
  не раньше строки ревизии в журнале (`_modified` ≥ времени ревизии); своя ревизия, ещё не видимая в Records, остаётся
  в ожидании, а не отбрасывается.
- №9 (средняя): `success=false` с «Failed to apply auto-layout: …» — общая обёртка, за ней может быть серверный таймаут
  платформы (`BpmnAutoLayoutService`) → исход `layout_failed` без повтора; повтор только при недоступном сервисе;
  «Invalid BPMN XML» / «cannot be empty» — `layout_rejected` без повтора. Отход от записки, раздел 9.6 («отказ —
  один повтор»): повтор опасен из-за общего контекста раскладки.
- Новые: ожидание завершается, только когда ни один артефакт приложения не в незавершённом статусе (`DRAFT`,
  `DEPLOYING`, `DEPS_WAITING`, `CONTENT_WAITING`), также при `unchanged`; `pending_statuses` в ответе; поле `workspace`
  патча читается и в компактном JSON, и в блочном YAML; системный id существующего пространства известен до проверки;
  в `app/patch` проверяются только цели операций (`id`, `ref`, `target`, `_workspace`…), а не ссылки в данных;
  навык велит при `unconfirmed` остановить развёртывания.

## 6г. Условия прогонов в Pi

- **Прогоны запускаются в видимом окне Terminal** (указание владельца 2026-11-10): скрипт прогона открывается через
  `osascript … do script`, владелец видит ход и сам подтверждает план, если не поручил это. Не `pi -p` в фоне.
  За ходом следим по JSONL сессии (`--session-dir`), живость — по PID процесса `pi`.
- Плагин стоит в Pi глобально из ветки `feature/app-from-spec-stage1`. Переменные окружения доходят до MCP-сервера
  (транспорт Pi наследует окружение процесса — проверено по коду `pi-mcp` и прогоном).
- **Каталог источников для замера — отдельный набор**, не весь `workspace-ctk`: в первом прогоне агент читал
  `citeck-ai/docs` (разборы дефектов прошлых прогонов) — для замера это утечка.

## 6д. Прогон `pi-run1` (2026-11-10, Pi 1.5.1, `deepseek/deepseek-flash`, рассуждения `high`)

ТЗ — заявки на закупку оборудования (не CRM, не договоры). Окно Terminal, план подтвердил владелец («ок»).

16,2 млн из кеша, выход 81 тыс. (из них рассуждения 30 тыс.); 3 развёртывания, 2 итерации цикла; 82 вызова оболочки.

- Итог: 11 артефактов `DEPLOYED` с первого развёртывания (включая шаблон нумерации и меню). Цикл нашёл и исправил два

  `commentRequired` не в `config` исхода). Основной сценарий пройден через Records API: подача → отказ без причины

- Журнал итераций сходится с коммитами (правка заявлена в итерации 1 — правка только файла процесса в `1cbd74b`).
- Вне пространства ничего не изменено (`_modified` после старта на типах, формах, журналах, меню, правах, процессах,
  шаблонах, приложениях, группах, пространствах — только `pigen1110:*`).
- Проверено мной в интерфейсе от `fet`: журнал открывается, две заявки, колонка состояния, пункт журнала в меню

3. Утечка: агент трижды читал `citeck-ai/docs` (разборы дефектов) и взял оттуда схему записи причины отказа.

5. После `bpmn_layout` файл переформатирован — текстовые правки агента молча не применились; он переписал процесс.
